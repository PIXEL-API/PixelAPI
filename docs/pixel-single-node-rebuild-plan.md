## 1. 目标与适用边界

### 1.1 希望得到什么

完成后，项目是一套以单个活动应用进程为运行基础的 API 服务：

1. 用户继续登录、管理 API Key、查看额度与使用记录。
2. 账号所有者和管理员继续管理账号、凭证、代理、分组及模型权限。
3. 客户端继续使用已保留协议，调度、流式输出和用量计费保持可验证的一致性。
4. 管理后台不再出现集群节点、集群操作、节点排空和跨节点缓存刷新。
5. 令牌刷新、订阅过期、备份、用量清理等业务任务继续在本机执行。
6. 对管理员保存配置的行为，本机缓存及时更新，不依赖集群消息广播。
7. 项目只有清晰的主部署方式，历史示例与日常运行配置不再混杂。
8. 开发人员修改某个业务规则时，能够找到明确的实现位置，减少复制和跨功能改动。

必须区分四类“臃肿”：

1. **源码维护负担**：重复流程、职责混杂、失效接口。
2. **运行负担**：实际启动的后台任务、连接池、缓存、请求体和日志处理。
3. **构建负担**：多套应用依赖、发布矩阵和测试运行方式。
4. **本地磁盘负担**：node_modules、.next、旧二进制、日志和压缩包。

删除旧二进制会减小工作区；拆大文件会改善维护；删除实际运行的集群任务才可能减少相应运行开销。不能把三种收益混为一谈，也不能承诺未经测量的内存下降比例。

## 3. 功能保留与裁剪矩阵

### 3.1 核心必须保持可用

| 功能 | 用户或管理员看到的结果 | 首批重构规则 |

| 登录、身份、会话、API Key | 登录和已有 Key 继续可用 | 不更换身份归属、Token 含义或 Cookie 安全边界 |

## 4. 集群完整删除设计

### 4.1 “单机”的准确含义

本方案中的单机是：**同一套业务数据同一时间只有一个活动应用进程执行后台写任务。**

一台服务器同时运行新旧两个版本，仍然是两个执行者。本机锁不能协调它们。删除集群租约后，上线和回滚不允许两个版本同时执行令牌刷新、备份、清理、结算等写任务。

本轮不是把 cluster.enabled 长期改为 false。最终产物不再初始化集群身份、心跳、跨节点任务租约、集群操作队列和缓存版本协调。

### 4.2 删除的功能

- 集群节点列表、详情和节点身份。
- 节点心跳、存活 TTL、离线节点保留清理。
- 管理员远程 drain/resume 操作。
- 集群任务租约、续租、fencing token 和归属判断。
- 跨节点操作队列及执行状态。
- 集群缓存版本表的运行时推进、广播与对账。
- 集群专用配置、前端菜单、API、类型和翻译。
- deploy/cluster 中的 Caddy、节点环境、systemd 与防火墙示例。

### 4.3 必须保留的同机功能

| 集群附近的现有能力 | 删除集群后的处理 | 不能误删的原因 |
|---|---|---|
| 普通账号筛选、容量、sticky session | 原业务规则继续执行 | 这是 API 网关账号调度 |
| 请求并发槽和消息队列 | 保留 | 单机同样会有并发与资源竞争 |
| 本机定时任务 | 保留真实回调、context、停止等待 | 没有多节点也需要刷新、清理、结算 |
| 本机任务防重与备份互斥 | 保留现有实现 | 防止一次任务未完成又触发下一次 |
| 业务幂等与交易锁 | 保留 | 不是集群租约的替代物，也不能因单机取消 |
| 账号房间 drain/退出流程 | 首批保持 | 属于 Account Share，和节点 drain 不同 |
| 缓存刷新与 API Key 失效 | 保留 | 配置保存后必须对下一次请求生效 |
| HTTP/SSE/WS 生命周期清理 | 保留 | 避免断流、悬挂连接和漏计费 |
| 数据库迁移锁 | 保留 | 保护迁移执行，不属于待删集群控制面 |
| PostgreSQL、Redis | 保留 | 仍承载核心数据、缓存、限流及调度 |

### 4.4 任务逐项回归本机执行

当前 ClusterTaskExecutor.Run 已有非集群直接执行回调的分支。优先复用真实业务逻辑，不再设计一个通用任务平台。

| 任务组 | 目标结果 | 特别检查 |
|---|---|---|
| Token 刷新、账号到期、异常清理 | 按原频率执行 | 取消、失败分类、持久化和缓存失效 |
| 代理到期、订阅到期 | 按原业务规则处理 | 所有者限制、备用代理、额度及订阅状态 |
| 用量聚合、用量清理、幂等清理 | 正常聚合及清理 | 运行中防重、批大小、超时、归档顺序 |
| 备份、备份过期清理 | 继续执行 | 直接调用执行器的入口必须改造；保留备份/恢复互斥 |
| 分组费率与返佣周期 | 对保留业务继续执行 | 不因去 Cluster 导致价格周期或邀请码周期停转 |
| 共享账号、支付订单到期、活动发奖 | 对保留业务继续执行 | 业务幂等、结算和历史状态不能改变 |
| 渠道监控、定时测试、Ideas、Ops | 按实际保留范围处理 | 区分“不保留业务”和“仅移除租约包装” |

迁移规则：

1. 查明每个执行器调用的业务函数与启动/停止位置。
2. 如果已有本机分支，收敛到该分支。
3. 如果直接调用执行器，显式调用原业务回调并保留错误返回。
4. 保留任务自己的互斥、防重、context、超时和幂等。
5. 去除没有消费者的租约参数和依赖。
6. 逐任务验证启动一次、执行一次、失败可见、退出能停止。
7. 不把所有依赖简单置为 nil；当前部分任务在这种情况下会报错并停止业务执行。

### 4.5 本机缓存更新

目标行为是：管理员保存渠道、系统配置或审核策略后，后续请求使用新状态。

保留：

- ChannelService 的本机 ReloadCache 及防旧构建覆盖新缓存的 generation 逻辑。
- SettingService 已有的配置更新与缓存刷新。
- ContentModeration 的本机配置替换。
- 分组关联变化后的 API Key 鉴权缓存失效。
- 前端 HTML 注入配置缓存和嵌入来源更新。
- 原有调度快照/outbox 机制中仍被单机业务需要的部分。

删除：

- 仅用于通知其他节点的版本推进。
- 集群 Pub/Sub 唤醒。
- 集群版本对账和 pending 重试。
- 无消费者的集群缓存表访问。

不能仅凭出现 Redis、version、outbox 或 cache 就删除。它们是否属于集群，必须按实际消费者判断。

### 4.6 单机健康、就绪与退出

这是先于 ClusterRuntime 删除完成的前置改造。

| 入口或状态 | 目标含义 |
|---|---|
| /health 与 /health/live | 进程可响应，保持现有存活探测用途 |
| /health/ready | 启动初始化完成，关键依赖处于有效检查结果中，且未开始退出 |
| 启动中 | 不接收业务流量，不报告 ready |
| 关键依赖失败或状态无法确认 | ready 返回失败，不伪造健康 |
| 停止或重启开始 | ready 先失效，再停止接收新业务请求 |
| 正在处理的 HTTP/SSE/WS | 按现有取消和有界等待规则结束，并完成必要用量处理 |
| 资源释放 | 先业务任务和连接池，后 Redis/数据库 |

实现建议：

- 只抽取必要的进程生命周期状态和健康快照，不创建第二套集群运行时。
- 探测使用有界超时和可判定新鲜度的结果，避免每次健康请求触发全量数据库扫描。
- 迁移兼容在启动阶段完成；不在每次 readiness 请求中重跑迁移。
- 保留关闭流程的等待、超时和错误记录。
- 单独验证 WebSocket 退出，不能仅凭 HTTP Shutdown 成功就宣称所有 WS 已结束。
- 旧 readiness JSON 中如有外部消费者使用的字段，先登记消费者与兼容窗口；不以保留字段为由继续伪报健康。

### 4.7 集群 API 与数据退役

前端删除 /admin/ops/cluster 页面和菜单。后端删除该组管理接口的注册、handler 与专有类型。旧集群客户端应得到明确的接口下线结果，不能被 SPA 页面或成功空响应吞掉。

如果选择当前项目渐进精简，首个代码退役版本：

- 不再执行集群业务表读写。
- 保留历史 SQL 文件及其内容。
- 保留 cluster_instances、cluster_task_leases、cluster_operations、cluster_cache_versions 等历史结构。
- 不运行全 Redis 清空，不批量删除命名相似的键。
- 不自动清除集群历史操作或迁移账本。

“代码不再运行集群”可以先完成；“物理删除历史表”属于后续单独的数据治理。历史迁移在安装新库时仍可能创建这些表，这是保留同一迁移链的结果，不等于运行时仍支持集群。

## 6. 公共流程抽取与核心服务整理

### 6.1 网关：共享规则，不强制所有协议同一顺序

以下是职责图，不是所有 Handler 必须遵循的统一执行顺序：

~~~text
身份与作用域 ── 模型/渠道策略 ── 额度与资格
                          │
                    账号候选与调度
                          │
                 原协议的转发和流式处理
                          │
                  用量、计费、错误与审计
~~~

每个入口都应先记录自己的阶段顺序，再在原位置调用共享规则。HTTP、Responses、WS、Gemini 原生入口、图片与媒体入口不能因为重构被强制转换为同一个请求结构。

建议逐块整理：

| 职责 | 目标效果 | 首批限制 |
|---|---|---|
| 入口解析与请求大小管理 | 参数来源和限制清楚 | 保留原协议解析与内存预算，避免多次复制大请求体 |
| 模型/渠道解析 | 列表、写入校验和网关终检口径一致 | 不让展示模型自动变成可调用权限 |
| 账号资格与候选 | 判断位置集中、原因可追踪 | 不合并“没容量”与“上游故障” |
| 重试与会话 | 保持正确归属和重试窗口 | 已输出内容后不随意换账号或换组 |
| 上游传输 | provider 差异有明确位置 | 不重建统一 HTTP 客户端绕过现有代理/TLS策略 |
| 流式处理 | 终止、取消、用量可验证 | 不吞上游错误或伪造成功完成 |
| 计费与使用记录 | 价格和幂等规则唯一 | 不改变原事务边界、锁顺序和结算快照 |

先在现有 Go 包内按职责拆文件，复用现有 helper；只有出现稳定、可独立验证的边界时才拆新包。不要为每个表增加一层新接口，也不建立泛化 Pipeline、事件总线或插件容器。

### 8.1 主部署方向

建议主路径为：

~~~text

    ↓

    ↓
~~~

### 8.2 Caddy 的处理

Caddy 是入口 Web 服务器/反向代理，不是推广返佣，也不是账号调度。

用一次请求说明：客户端访问你的域名，Caddy 在入口处理 HTTPS，再把请求转给 Go 应用，最后把应用的结果返回给客户端。仓库配置还包含健康检查、访问日志、客户端来源信息和压缩等设置。

仓库单机 Caddyfile 将请求转发到 localhost:8080；集群 Caddyfile 将请求分发给多个应用节点。它们不能混成一个删除对象。如果主部署采用 Nginx，由 Nginx 承担需要保留的入口职责，不必再为同一入口维护第二套 Caddy 配置。

| 范围 | 处理建议 |
|---|---|
| deploy/cluster/Caddyfile | 随集群目录退出 |
| deploy/Caddyfile | 不作为默认部署方案；是否保留示例由部署范围决定 |
| 服务器上的 Caddy | 本轮不操作，不因删仓库文件而假定服务器不存在该进程 |
| Nginx | 作为主入口时保留 HTTPS、真实 IP、流式、WS 和超时要求 |

删除 Caddy 示例只减少配置维护，不直接降低 Go 进程内存。

### 8.3 Docker 与测试容器

主服务改用单一二进制发布，不等于删除所有 Docker 使用。

- 生产 Compose、多架构镜像和多仓发布矩阵，按实际使用者收敛。
- PostgreSQL/Redis 集成测试仍可能需要隔离容器。
- 不为减少 CI 任务而删除交易、迁移和 Redis 语义验证。
- docs/site 是独立应用。其发布与主服务构建解耦；是否停止公开文档服务需另行决定。
- 修改 CI 触发规则时保护 required checks，不能让跳过的工作流阻断或绕过合并门禁。

### 8.4 依赖治理

| 依赖类别 | 本稿建议 | 验证要求 |

### 阶段 P1：失效链路整理

| 任务 | 主要范围 | 输出与验收 | 依赖 |

阶段验收：前后端构建及相关回归通过；无新增业务停用。

### 阶段 P2：补齐可独立运行的单机能力

**目标效果：** 即使没有 ClusterRuntime，系统也能准确就绪、执行后台任务、刷新缓存并正常退出。

| 任务 | 主要范围 | 输出与验收 | 依赖 |
|---|---|---|---|
| P2-1 单机就绪 | common routes、runtime、main | 依赖失败/未知/退出时非 ready；存活探测独立 | P0-4 |
| P2-2 单机退出 | shutdown、server、WS 清理 | 停止新请求、处理存量、有界释放 | P2-1 |
| P2-3 业务任务迁移 | 各 service 与 wire | 每个保留任务不依赖租约而真实执行 | P0-3 |
| P2-4 本机缓存保真 | Channel、Settings、Moderation、API Key | 写后本机生效，保留并发刷新保护 | P0-3 |
| P2-5 连接统计消费者整理 | server/http、统计消费者 | 必要统计保持，删除无消费者包装 | P2-2 |

P2-3 与 P2-4 可独立调研和验证；Wire 与启动文件由同一人整合，避免并发改同一组合入口。

### 阶段 P3：完整移除 Cluster

**目标效果：** 后台无集群菜单；运行时无节点注册、心跳、跨节点租约或缓存版本访问。

| 任务 | 主要范围 | 输出与验收 | 依赖 |
|---|---|---|---|
| P3-1 删除管理入口 | cluster handler/routes、frontend 页面/API/i18n | 无集群入口，旧路径下线行为明确 | P2 完成 |
| P3-2 删除协调实现 | cluster runtime、repo、task/cache 包装 | 就绪、退出、任务、本机缓存和必要连接统计均已独立 | P2 全部验收完成 |
| P3-3 清理启动依赖 | wire.go、main、router、http、cleanup | 从源 Provider 修改并重新生成 wire_gen | P3-2 |
| P3-4 清理配置 | config、env 示例、相关测试 | 过时 CLUSTER 设置不静默误导；说明单实例要求 | P3-3 |
| P3-5 删除集群部署目录 | deploy/cluster | 无多节点部署入口 | P3-4 |
| P3-6 验证零集群运行依赖 | 静态引用与隔离环境 | 运行时无集群表访问；历史迁移允许保留引用 | P3-1 至 P3-5 |

阶段验收：在不存在集群运行时对象的条件下，核心请求、任务、配置生效、错误与退出全部通过。

### 阶段 P4：减少重复并拆分大文件

**目标效果：** 用户行为保持，常用修改点集中，页面与服务更容易理解。

| 任务 | 主要范围 | 输出与验收 | 依赖 |
|---|---|---|---|
| P4-1 OAuth 去重 | auth handlers、composables、callback views | 公共流程唯一；provider 差异用例通过 | P0-4 |

| P4-5 管理/设置/仓储整理 | Admin、Settings、Accounts、Usage | 每块有单一职责，事务和字段语义不变 | P4-4 可分批 |

每个拆分任务先保持接口，再移动调用；不同时改协议、价格、数据库结构和页面设计。

### 阶段 P5：按选择裁剪业务与构建

**目标效果：** 不需要的业务按完整生命周期退出，而不是只隐藏菜单。

| 任务 | 主要范围 | 输出与验收 | 依赖 |
|---|---|---|---|

| P5-2 在途状态处理设计 | 订单、共享、奖励、返佣等 | 明确停止新建、完成存量、查询保留顺序 | P5-1；数据读取另行授权 |
| P5-3 整链裁剪 | UI/API/tasks/config/dependencies | 退出功能不运行，保留功能无悬空引用 | P5-2 |
| P5-4 部署与 CI 收敛 | Docker/Caddy/发布矩阵/docs CI | 主路径唯一，集成验证和 required checks 保持 | 部署范围选择 |

### 阶段 P6：发布准备与回滚演练

**目标效果：** 新版可验证、可恢复，且单实例约束在切换时成立。

1. 汇总变更范围、契约结果、性能对比和未解决风险。
2. 生成包含正确前端产物的 Linux 发布包，校验版本与文件摘要。
3. 在隔离环境验证启动、故障、任务、退出和回滚。
4. 对生产做用户授权范围内的当前配置与使用方式核对。
5. 切换前停止旧进程及后台写任务；确认没有第二个活动写进程。
6. 按授权发布流程切换产物和配置，再启动新版。
7. 验证 ready、真实请求、SSE/WS、错误率、内存趋势和任务执行。
8. 失败时停止新版，恢复旧产物和匹配配置，再启动旧版。
9. 无破坏性 schema 改动时优先代码/配置回滚；若另行批准过数据删除，按独立恢复方案执行。

不在同一生产数据集上同时启动新旧完整应用来实现“无缝切流”，除非已经有经验证的单写协调方案。本方案默认采用可控的短暂切换窗口。

## 11. 风险、修复前后与回退边界

| 风险 | 修复前状况和影响 | 设计完成后状况和影响 | 回退/验证边界 |
|---|---|---|---|
| 粗暴删除执行器 | 正常任务可能不再执行 | 业务任务与跨节点租约分开 | 每个任务必须证明实际执行 |
| 单机固定 ready | 依赖失败仍可能显示就绪 | 真实依赖与退出状态参与就绪判断 | 不把检查异常吞成成功 |
| 删除缓存协调时误删本机更新 | 管理员保存成功但请求使用旧配置 | 本机刷新独立，跨节点通知退出 | 并发写后读验证 |
| 把统一流程图当代码顺序 | 改变协议阶段、重试或计费行为 | 共享规则在原入口原位置调用 | 按入口阶段矩阵复核 |
| OAuth 过度统一 | Cookie、身份冲突或授权模式被改变 | 公共骨架复用，差异仍显式存在 | provider 专有反例必须保留 |
| 去集群后双进程运行 | 任务重复、清理或结算竞态 | 发布确保一个活动写进程 | 切换与回滚都遵守 |
| 把无调用桩当实际故障 | 误禁用真实测试和刷新 | 只清理符号及接口残留 | 调用链双证据 |
| 误删正常备份 | 失去备份、恢复与归档 | BackupService 完整保留 | 不以文件名判断功能归属 |
| 直接删迁移/表 | 升级或回滚失败、历史不可读 | 首批保留历史链和结构 | 数据清理独立授权 |
| 未选择就裁掉返佣/支付/共享 | 用户权益、订单与账单受损 | 保留至逐项确认 | 已发生权益与在途状态先处理 |
| 为减依赖重写底层库 | 回归多而收益不明 | 先复用、再测量、最后择机替换 | 独立改动与完整协议验证 |

## 12. 收益测量与完成标准

不预先承诺删除多少比例代码、降低多少内存或提高多少吞吐。

| 维度 | 应采集的对比项 | 可以确认的完成效果 |
|---|---|---|
| 功能面 | 菜单、路由、后台任务与配置 | Cluster 整链退出，保留业务完整 |
| 维护性 | 重复流程、职责跨度、调用位置 | 一个规则有明确唯一维护点 |
| 构建 | 同环境冷/热构建、CI 时长 | 只报告实际缩短或持平结果 |
| 产物 | 发布包大小、前端 chunks | 区分依赖安装体积与实际交付体积 |
| 运行 | RSS、goroutine、CPU、连接、空闲任务 | 不再有集群心跳/租约/版本协调开销 |
| 请求 | 吞吐、错误率、TTFT、长流稳定性 | 相同负载下无未解释退化 |
| 数据 | 任务写入、重复结算、迁移差异 | 核心语义不变，集群运行读写退出 |
| 恢复 | 启动、退出、回滚耗时与结果 | 可以恢复旧产物和匹配配置 |

功能面减少是确定的设计目标；性能收益必须由同条件测量证明。单次 /health/ready=200 或一次成功请求不能证明长流、后台任务和内存已经稳定。
