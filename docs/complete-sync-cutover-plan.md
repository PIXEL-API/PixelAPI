# 完全同步与单实例切换计划

## 结论

新服务器上让应用与 PostgreSQL 同机运行，可以消除应用到数据库之间的公网网络往返，通常会缩短事务持续时间并降低锁等待概率。但 PostgreSQL 的行锁、事务锁和唯一键冲突仍可能在单机内发生，不能承诺“绝对无锁”。

本次切换必须保证同一时间只有一个应用实例写入业务库；旧服务停止后再做最终同步，新服务启动前不允许旧实例恢复。

## 当前已知状态

- 旧生产服务 `pixel.service` 已恢复，健康检查为 200。
- 旧库没有创建备份，本计划不增加源库全量备份。
- 新库已经导入完整 schema 和一批核心数据，但在线导入期间源库仍在写入，存在少量行数和余额时间差，不能直接作为最终切换数据。
- 迁移范围约 89 张核心表、约 8.39 GB；日志、使用记录、账本、结算等大表不迁移。
- 新服务器上的应用进程当前保持停止；新 PostgreSQL 只作为接收端。

## 阶段一：切换前只读预检

1. 检查旧机：`pixel.service`、PostgreSQL、Redis、nginx、磁盘、内存和健康接口。
2. 检查新机：PostgreSQL 18、扩展、UTF-8 数据库、磁盘余量、Redis 安装状态；确认 `pixel.service` 未启动。
3. 对照应用配置：新机数据库使用本地 Unix socket 或 `127.0.0.1`，Redis 使用本机地址；确认数据库角色、密码和扩展均已准备。
4. 保持旧机现有稳定配置：使用记录 worker 数量为 1，关闭自动扩容；新机只运行一个应用进程和一个后台写入者。
5. 预先验证新机但不启动应用：使用 `curl --resolve` 通过新机 IP 检查 nginx/TLS/静态资源和后端端口。

**放行条件：**旧库锁等待为 0；新库可连接；新机磁盘有足够空间；DNS/Cloudflare 记录确认最终指向新机。

## 阶段二：短暂停机并做最终一致同步

推荐采用“完整重载核心表”而不是猜测增量边界，避免遗漏余额、订单和账号更新。预计停机窗口保守预留 15–30 分钟。

1. 在 DNS/边缘层开启维护或先阻断新请求进入旧应用。
2. 优雅停止旧 `pixel.service`，等待现有请求完成；若进程因积压无法退出，只强制结束应用进程，不停止 PostgreSQL/Redis。
3. 确认旧库没有应用事务、锁等待和迁移 COPY 任务；此时源库仅保留数据库服务。
4. 仅在新机目标库上删除并重建目标数据库（UTF-8、`template0`），重新导入 schema；不触碰原库。
5. 从旧库以只读方式导出筛选的 89 张核心表，使用 PostgreSQL 压缩归档；新机用 `pg_restore --disable-triggers` 接收。导出设置锁等待超时，避免等待源库锁。
6. 导入完成后，在源库和目标库分别核对：核心表行数、`users.balance` 总和、`users.points_balance` 总和、账号数、API key 数、订单数、兑换码数和系统配置。

**放行条件：**源库与目标库关键行数及余额汇总一致；目标库没有恢复失败、外键错误或残留 COPY；旧服务仍保持停止。

## 阶段三：新机单实例启动

1. 先启动新机 Redis，确认 6379 可用；Redis 中的会话、队列和临时状态不属于 PostgreSQL 数据同步，若不迁移，用户可能需要重新登录。
2. 写入新机应用配置：数据库本地 socket/localhost、Redis 本地地址、生产域名和密钥；不要把旧机远程数据库地址留在配置中。
3. 启动新机 `pixel.service`，只启动一个实例；确认 usage-record worker 仍为单 worker、自动扩容关闭。
4. 通过新机本地地址、服务器 IP 和 `curl --resolve` 做健康、登录、API key、余额读取、订单读取和一次受控 API 请求验证。
5. 观察 2–5 分钟：`pg_stat_activity` 锁等待、慢查询、应用错误、Redis 队列、内存和 CPU。

## 阶段四：DNS 接管与稳定观察

1. 确认新机应用验证通过后，将 DNS/Cloudflare 记录切换到新机；保留旧机应用停止状态，避免 DNS 缓存用户继续写旧库。
2. 旧机 PostgreSQL 可以暂时保持运行用于只读核查，但旧应用、旧 worker 和旧 Redis 写入者必须保持停止。
3. 观察至少一个完整业务高峰周期，再考虑关闭旧机数据库服务。
4. 迁移工具和临时认证工具全部清理，记录最终切换时间和两端校验结果。

## 锁风险与控制

| 场景 | 同机后的影响 | 控制措施 |
|---|---|---|
| 应用到数据库网络往返 | 明显降低，事务通常更短 | 使用本地 socket/localhost |
| 多实例同时写同一行 | 仍会发生 | 只启动一个 `pixel` 实例 |
| usage_logs 高并发写入 | 仍可能出现 tuple/transactionid 等待 | worker=1、关闭自动扩容、监控锁等待 |
| 长事务或后台任务 | 仍可能阻塞业务 | 切换前停止旧应用并确认无长事务 |
| 目标导入外键顺序 | 只影响新库 | 目标端使用 `pg_restore --disable-triggers` |

## 回滚边界

- 在新应用尚未产生写入前，可以把 DNS 指回旧机并重新启动旧服务。
- 新应用一旦开始向新库写入，旧库不会自动得到这些新写入；没有源库备份，也没有建立复制链路，因此不能承诺无损回滚。
- 如需在新库已写入后回滚，必须另行做反向增量同步或再次停机核对，不能直接启动旧实例。

## 验收标准

- 新机域名访问稳定，健康检查和关键业务请求成功。
- 新机 PostgreSQL 锁等待持续为 0 或在可接受阈值内，未出现持续 transactionid/tuple 等待。
- 源库旧应用保持停止，确认没有第二个 worker 或第二个应用实例写库。
- 关键表行数、余额汇总、积分汇总和配置核对一致。
- 未修改原库数据、结构、配置、复制槽；未创建全量备份。
